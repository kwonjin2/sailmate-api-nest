# 학습 진행 판정

## 현재 상태

- 공식 진행 상태: 1주차 완료, 2주차 진행 중.
- 실제 선행 학습: 2주차 DTO, ValidationPipe, 입력 정규화 및 관련 e2e 실습을 진행했다. 이 결과는 보존하며 반복하지 않는다.
- 이전 AI의 1주차 완료 선언은 학습자의 설명 증거를 명시적으로 확인하지 않아 성급했다. 미확인은 이해 부족 판정이 아니라 증거 부족을 뜻한다.

## 1주차 종료 기준 점검

기준: `curriculum/week-01.md`의 Acceptance Criteria와 Verification.

| 기준 | 상태 | 증거 또는 남은 확인 |
| --- | --- | --- |
| 학습자 직접 초기화 | 충족 | 사용자 인계 내용의 초기화 완료 보고 |
| 개발 서버 실행 | 충족 | 사용자 서버 실행 및 curl 실습 보고 |
| GET /health의 200과 응답 | 충족 | 기존 검증 보고와 1주차 learning log |
| DB 없는 API에서 두 HTTP method 사용 | 충족 | GET/POST /gatherings 구현과 사용자 호출 결과 |
| 요청 전체 흐름을 말로 설명 | 충족 | 학습자가 GET /gatherings의 라우팅, Controller 메서드, Service 호출, 반환 흐름을 설명 |
| Controller와 Service 책임을 예시로 설명 | 충족 | 학습자가 Controller의 요청 전달과 Service의 생성·저장 책임을 설명. DI와 메서드 호출의 차이는 리뷰로 보완 |
| 1주차 학습 기록 | 충족 | docs/learning-log.md의 1주차 기록 |
| 성공·실패 요청, 콘솔 로그와 HTTP 응답 확인 | 충족 | POST 201과 GET 200에서 동일 id 확인, 기존 빈 body 결과 확인. 사용자 제공 서버 로그에서 0 errors, 의존성 초기화, GET/POST 라우트 등록, 앱 시작 확인 |

모든 종료 기준을 충족하여 1주차를 종료한다. 추가 설명 반복이나 e2e 작성 없이 2주차의 남은 기준으로 진행한다.

## 2주차 선행 작업 및 남은 기준

- 사용자 검증 완료 보고: DTO 입력 규칙, 400 거절, 허용되지 않은 필드 거절, trim 후 생성과 조회, 실패 요청의 저장 방지.
- 사용자 이해 확인: whitelist와 forbidNonWhitelisted 차이, trim 제거 시 공백 입력이 길이 검증을 통과하는 이유, await로 POST 이후 GET 순서 보장.
- 현재 입력 검증 e2e 확장 실습은 종료한다. 숫자 입력 테스트 등 추가 경계값은 현재 필수 진도 조건으로 추가하지 않는다.
- 남은 필수 작업: 존재하지 않는 리소스의 404, pagination 구현·검증, 각 API 상태 코드 선택 설명, API contract 문서, 2주차 학습 기록.
- 409는 제목 중복을 억지로 금지하지 않는 선택과 근거를 기록한다. 구현할 실제 충돌 규칙이 없다면 커리큘럼의 선택 여부 설명으로 처리한다.
- 커밋 전 검증: build와 lint 통과, unit 1개와 e2e 5개 통과. 공백 전용 테스트가 실제 파일에 포함된 것을 확인했다. e2e는 샌드박스의 포트 바인딩 제한으로 최초 실패했으나 권한 확장 후 모두 통과했다.
